# MEDCORE — Installation Guide

## What you receive
A MEDCORE BOX or vendor package containing the MEDCORE software, a bundled Node.js
runtime, and the installer. You do **not** need to install Node, PostgreSQL, or
edit configuration files by hand.

## Prerequisites (handled or checked by the installer)
- A 64-bit Windows or Linux machine for the BOX.
- PostgreSQL 16 reachable by the BOX (bundled or installed by the vendor package).
- ~2 GB free disk for the app; more for data and backups.
- For Arabic/RTL PDF printing: a Chromium runtime (bundled on boxes that need it).

The installer runs a **preflight** that verifies the Node version and the
PostgreSQL client tools, and stops with a clear message if something is missing —
without changing anything (`vendor.bat install` calls `bootstrap.mjs --check`
internally first).

## Install (Windows)
From the MEDCORE folder:
```
vendor.bat install
```
This is **idempotent** — safe to run again; it never overwrites an existing
configuration or database. It performs:
1. Preflight prerequisite checks.
2. Configuration generation — writes `server/.env` with **freshly generated
   secrets** (`AUTH_PEPPER`, `BACKUP_ENCRYPTION_KEY`). Secrets are generated
   locally and never printed.
3. Database initialization and migrations (transactional; never left half-applied).
4. Administrator bootstrap — creates your first clinic and an `admin` account with
   a **one-time password printed once**. Store it and change it at first sign-in.

Then:
```
vendor.bat start
vendor.bat health
```
`health` should report `"status": "ok"` with the applied-migration count.

## Install (Linux / manual)
The same logic runs cross-platform:
```
cd server && npm ci --omit=dev
node install/bootstrap.mjs        # or --check for preflight only
npm --prefix server run start     # loads server/.env automatically
node install/medcorectl.mjs health
```

## Configuration
All configuration lives in `server/.env` (generated by the installer). You do not
normally edit it. Key values:
- `DATABASE_URL` — the local PostgreSQL database.
- `AUTH_PEPPER`, `BACKUP_ENCRYPTION_KEY` — generated secrets (keep safe; rotating
  the pepper invalidates existing passwords).
- `LICENSE_DIR`, `BACKUP_DIR` — durable state folders (kept across upgrades).
- `LICENSE_PUBLIC_KEY` — the vendor public key, pinned at packaging time.

Configuration is validated at startup; the BOX refuses to start in production with
a placeholder secret.

## Upgrading and reinstalling
- **Upgrade:** `vendor.bat update` (takes a backup, migrates, rebuilds, verifies —
  see [OPERATIONS](./OPERATIONS.md#updates)).
- **Reinstall:** re-run `vendor.bat install`; existing data and the `state/`
  folder (backups, license) are preserved.
- **Uninstall:** `vendor.bat uninstall` stops the service and explains safe
  removal; your database and `state/` are not deleted automatically.

## Where things live
- `server/` — the backend application.
- `web/` — the browser interface (served locally).
- `install/` — bootstrap + operations scripts and logs (`install/logs/`).
- `state/` — durable data: `state/backups`, `state/license`.
